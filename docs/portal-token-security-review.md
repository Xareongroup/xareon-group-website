# Portal token security review

## Current design

- Customers have a UUID `portal_token`, a unique index, and `portal_created_at`.
- Tokens are generated by database/default UUID generation and regenerated through the customer portal regeneration flow using `randomUUID()`.
- Server-only `authenticatePortalToken` rejects short tokens and resolves the customer. Portal utilities then add `customer_id` to every resource query.
- Token regeneration replaces the old token, immediately invalidating URLs based on it, and records portal activity.

## Strengths

UUID token entropy is suitable for unguessable bearer links when URLs are handled as credentials. The portal never exposes the service-role client to browsers, and document downloads use a short-lived storage signed URL after ownership validation.

## Risk and recommendation

There is no enforced portal-token expiry or maximum age; `portal_created_at` is recorded but not checked. A leaked link continues to work until an admin regenerates it. This is a medium-risk operational gap for a customer-facing bearer-token portal.

Recommended future additive migration: add `portal_expires_at timestamptz nullable`, populate a conservative default for newly generated tokens, and update token authentication to reject expired values. Include a customer-friendly reissue workflow and staged migration plan for existing customers. Do not implement this during the current readiness review because expiry policy, duration, and customer communication require product approval.

## Operational guidance

- Treat portal URLs as credentials: avoid copying them into analytics, support tickets, or logs.
- Regenerate a token after suspected disclosure or customer access revocation.
- Set the canonical HTTPS `NEXT_PUBLIC_SITE_URL`; do not send portal links built from localhost or a staging domain.
